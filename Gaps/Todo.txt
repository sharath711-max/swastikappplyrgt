### Fix 1 — RecordPage.js:156 (wrong column displayed)

Column header branches by record type ("Fine Weight" for certs, "Sample Weight" for tests) but `<td>` was using `fine_weight || sample_weight` for both:

`getWeights` used `|| item.sample_weight` as fallback for both `gross_weight` and `test_weight`. When `test_weight = 0` (not yet entered), validation used `sample_weight` as test weight — completely different field. Purity validation could pass with wrong weight data.

// After (correct)

const test  = Number(item.test_weight  || 0);

Kanban board query returns only summary fields (`total`, `status`, `auto_number`, etc.) — no `gross_weight` or `net_weight`. `hasWeightLoss` always returned false. Removed `hasWeightLoss`, `weightLossAmount`, `showWtLoss`, weight loss badge JSX, and unused `FaExclamationTriangle` import.

## ✅ K11 — Backend: multer Breaks AsyncLocalStorage — DONE

**File:** `backend/routes/certificateRoutes.js` — routes using `upload.single('photo')`

**Problem:**
`POST /certificates/:id/results` and `POST /certificates/with-photo` use multer middleware. Multer's internal processing breaks the AsyncLocalStorage chain. Inside the route handler, `getRequestId()` returns a stale or wrong value. This causes `transaction()` to see `inserted.changes === 0` (request_id already in `request_log` from a different context), triggering "Request is already processing" 409 errors even on first-call requests.

**Impact:**
Save-draft via `POST /certificates/:id/results` fails through the HTTP layer with "Request is already processing". Service layer works correctly (tested directly — PASS).

**Fix required:**
Wrap the route handler in `AsyncLocalStorage.run()` to re-enter the correct context after multer processing. Or restructure so `upload.single('photo')` only applies to routes that actually handle photos, and separate the JSON-only results save to a non-multer route.

### Checklist — Applied Fix ✓
- [x] `POST /certificates/:id/results` with JSON body succeeds without "Request is already processing"
- [x] Photo upload path still works
- [x] Service-layer idempotency unaffected

## ✅ K15 — Finalize Idempotency & Conflict Handling — DONE

**Problem:**
Finalizing a record that was already DONE (e.g. via double-click or concurrent session) triggered the `trg_immutable_gold_test` DB trigger. This raised an error that was wrapped into a 500 `SystemError` by the backend, resulting in a generic "Something went wrong!" response instead of a meaningful 409 Conflict. Additionally, concurrent requests could race between the code-level status check and the final DB update.

**Files changed:**
- `backend/services/v2/errors.js`
- `backend/services/v2/testService.js`
- `backend/services/v2/certificateService.js`

### Fixes
1. **Graceful Conflict Mapping:** Updated `rethrow` in `errors.js` to detect SQLite trigger errors containing "finalized" and map them to a 409 `BusinessError` with code `IMMUTABLE`.
2. **Transaction Hardening:** Switched all critical write transactions in `testService.js` and `certificateService.js` (finalize, complete, save-draft) to `.immediate()` mode. This forces concurrent writers to serialize at the database level, ensuring the status check always reads the most current state.

### Checklist — Verified ✓
- [x] Finalizing an already DONE record returns 409 Conflict with "gold_test is finalized and cannot be modified"
- [x] Concurrent finalize requests handle race conditions correctly via IMMEDIATE locks
- [x] No generic 500 errors on terminal state transitions
